# Development Guidelines

## Code Architecture

- **MCP Integration**: Always utilize MCP (Model Context Protocol) tools and resources first before implementing custom logic. Check available MCP servers for existing solutions.
- **Cross-Platform Consistency**: The application targets three platforms — Electron (GUI), CLI, and Android (Capacitor). All core business logic in `src/ts/core/` must be shared; only the platform families (`src/ts/platforms/`) and the shells (`src/ts/shells/`: entry points, bridges, native-service wrappers) are platform-specific.
- **Layers and the Platform port** (deep reference: `docs/architecture.md` §12): `src/ts/` is `core/` (shared logic), `platforms/{node,webview,headless}/` (one runtime each), `shells/{electron,cli,web,capacitor,headless}/` (one entry point each), `react/` (UI only) and `appPaths.ts` at the root (its `__dirname/../..` depth must match the bundled `out/main/app.js`). Core imports only core; a platform imports core; a shell imports core, platforms and react, never another shell; react imports react and core. The `layer-boundaries/no-cross-layer-import` Oxlint rule (`scripts/lint/layer-boundaries.mts`) is an **error** — type-only imports and `typeof import()` are exempt (they leave no runtime edge), which is why core types such as `core/types/ipc.ts` and `core/ipc/releaseUpdates.ts` may keep `typeof import()` references to the Electron-only handler modules (`shells/electron/misc.handlers.ts`, `update.handlers.ts`). What differs per platform reaches core through the **Platform port** (`src/ts/core/platform/port.ts`): `platform().storage / paths / assets / wipe / native / windows / capabilities / http`, installed once by the shell's `platform.ts` (`installPlatform`; a second, different install throws). **Install before the logger**: each `shells/<shell>/platform.ts` is its entry's first import and its static imports are only the port, the family builder, type-only imports, Node builtins, and dependency-free core modules that reach neither the logger nor `platform()` (such as `core/plainObject`; on Electron also `index/session.ts`) — everything else is a call-time `require` — because the logger reads `platform()` at load; `tests/ci-validation.test.ts` (metafile load-time chain) and `tests/shells/loadOrder.test.ts` guard it.
- **Entry points**: Electron `src/ts/shells/electron/index.ts` (bundled by `scripts/build-main.ts` into `out/main/app.js`, with a source map, behind the `out/main/index.js` loader that package.json `main` points at — `pnpm start`/`dev` build it first; `out/` stays out of `dist/`, Capacitor's webDir) · CLI `src/ts/shells/cli/cli.ts` · Electron preload `src/ts/shells/electron/preload.ts` (the Logs window's reduced one is `src/ts/shells/electron/preloadLogs.ts`) · Capacitor bridge `src/ts/shells/capacitor/bridge/capacitor.ts` · Android headless background service `src/ts/shells/headless/index.ts` (a bare WebView the native `AutoVoteService` drives, one cycle per alarm) · web shell: server `src/ts/shells/web/server.ts`, browser bridge `src/ts/shells/web/bridge/web.ts`, page `src/ts/shells/web/page.tsx`, launcher `scripts/web-server.ts` (`pnpm web`). Each shell has a `platform.ts` beside its entry that installs the platform before anything else loads. The same React renderer (`src/ts/react/`) runs under Electron, Capacitor and the web shell; its voting loop is the plain-TypeScript controller `src/ts/core/autovote/controller.ts` (the React `AutovoteContext` is an adapter that builds its host), and the renderer still owns the timer (`docs/scheduling.md`).
- **API surface swap**: `src/ts/core/apiFactory.ts` selects real vs mock implementations at runtime based on `settings.mock`. All callers go through the factory — do not import `src/ts/core/api/*`, `src/ts/core/strategies/*` or `src/ts/core/mock/*` directly from business logic. `src/ts/core/api/` is the transport layer (api-client + endpoint wrappers, no `services/` imports); the real-mode composition over it (voting pass with join/claim pre-steps, entry-picking boost, title-pinned challenge read) lives in `src/ts/core/strategies/real/`, the mock counterpart in `src/ts/core/mock/` (`strategy.ts` over the `endpoints/*` fakes, assembled into `mockApiClient` behind the `mock/index.ts` facade).
- **IPC** (deep reference: `docs/architecture.md`): `src/ts/core/ipc/manifest.ts` is the dependency-free single source of truth for the `window.api` surface; both shells generate from it and CI enforces name-parity. Signatures travel through the `WindowApi` type (`src/ts/core/types/ipc.ts`, derived from the manifest + every `buildHandlers()`): a renderer call in a type-checked file is checked against its handler's parameters and result — only as precise as that handler's type annotations. Handler modules export `buildHandlers(deps)` only and are reused by the CLI, the web shell and Capacitor (no parallel impls); `core/ipc/invokeHandler.ts` holds the `IpcHandler` type and `invokeHandler`, the one place renderer arguments reach a handler. Electron registers them in `shells/electron/registerIpc.ts` through `registerHandlers()` in `shells/electron/registerHandlers.ts`, which applies `isTrustedSender` and the Logs-window channel checks before calling `invokeHandler`. Handlers **return `{success,error}` — never throw to the renderer**.
- **Persistence**: use `createJsonStore()` (defined in `settings/jsonStore.ts`, imported via `settings/storage.ts`) for platform-aware JSON; don't hand-roll `fs`. The storage transports live in the platform families (`platforms/node/` fs, `platforms/webview/` Preferences, `platforms/headless/` native bridge) and core reaches them through `platform().storage`, never by testing which family it runs on. The settings blob is `config.json` (`ConfigV2`, `src/ts/core/types/config.ts`; `gurushots-config` on Android). Node-side platform differences = the Platform port (`platform()`; `src/ts/core/runtime.ts` is only the env flags, the one reader of the process environment); renderer-side = `platformKind()` (`src/ts/core/platform/kind.ts`), which the web and Capacitor bridges mark when they install `window.api`. Paths to the app's own files (HTML, preload bundle, assets, the dev model cache) come from `appPath(...)` (`src/ts/appPaths.ts`, reached through `platform().paths.appPath`) — never a module's own `__dirname`, which is the bundle's directory once the main process is bundled.

## Application Domain & Invariants

> Deep reference: **`docs/architecture.md`** (and `docs/scheduling.md` for the timer engines). These are invariants an edit must not violate.

- **Voting pass**: one shared loop `runVotingPass` (`src/ts/core/services/votingOrchestrator.ts`, per-phase runners in `src/ts/core/services/votingOrchestrator/`) for real+mock — never fork it; inject differences via `deps`. The per-challenge runners are **sequential, never parallelised** (shared challenge-object mutation). Rule precedence in `_runVotingRules` (`src/ts/core/services/decisions/ruleEngine.ts`; callers reach it through the `services/VotingLogic.ts` facade's `evaluateVotingDecision` / `evaluateManualVotingDecision`) is load-bearing.
- **Two distinct sentinels — don't merge them**: for `exposureTarget`/`lastHourExposureTarget`, `0`/null = "target == trigger" (rule **stays active**); for `boostTime`/`emergencySubmit`/`keyUnlockedBoostTime`, `0` = feature **off**.
- **Sleep boost**: `services/boostGuard/suspendBoost.ts` → `runSuspendBoost` shares `runBoost`'s rules and is the only place per-challenge runners run in parallel. The quit guard (`shells/electron/windows/quitGuard.ts`) and the sleep boost share one selection, `imminentBoostChallenges`.
- **Scheduler**: single recursive `setTimeout` chain, no cron (the renderer's chain is the plain-TS controller `core/autovote/`, not React code; the renderer owns the timer); one decision point `computeNextCycleDelayMs`; invariant "never sleep past a boundary"; cancellation is a global flag that propagates by `return`, never `throw`.
- **API transport**: every POST goes through `src/ts/core/api/api-client.ts`. `makePostRequest` returns the body as the wrapper's response type `T`, or **`null` (failed request, or a body that is not a JSON object) — it never throws**; branch on `null`. Spends (`coins_unlock` in `api/join.ts`, the currency spends in `api/currency.ts`) go through `postOnce` instead — sent once, never retried — and answer a `PostOutcome` (`body` / `refused` / `unclear`, `api/postOutcome.ts`); never retry a spend or treat `unclear` as failed. Keep retry/backoff centralised; custom (Android) adapters must call `finalizeAdapterResponse`.
- **Settings storage**: `config.json` is the only stored settings file and the only source of truth. On the paired remote phone page, theme, language, `compactCards` and `compactCardActions` are kept on the device in `localStorage` under `gs-remote-view-prefs` — the one exception — and `config.json` stays the source of truth for everything else. `settings.json` is read once, for the import of a 1.x install (`settings/legacyImport.ts` over the frozen pipeline in `settings/importV1/`); the import marker (`v2-import.json`) says it has run, so a file that shows up later is not imported unasked. The load order in `settings/persistence.ts`: use `config.json` when it reads; refuse saves while it cannot be read; set a damaged one aside (`quarantineRaw`) and apply the defaults; import once when it is missing and the marker is not done — an import that may pass by itself blocks saves until it is retried, one that cannot writes the defaults with the failure in their import record and is done; defaults when there is nothing to import. The import marker and the title pins are `shared` stores (`createJsonStore`): change them with `updateNow`/`updateThrough`, never the Android window's cache written whole. The importer (`settings/importV1/`) is frozen.
- **Semantic lexicon** ranks auto-fill photos only — **never** the vote decision; `SEMANTIC_MATCH_FLOOR` is build-gated by `scripts/validate-lexicon.ts`, not hand-tuned.
- **Safety**: optional-chain every per-challenge API read (an unguarded throw aborts the whole pass); new-entry detection compares ids as **sets, not positions**; mock mode must pass `cleanupStaleMetadata: null` so it never touches the real `metadata.json`.
- **Scenarios** (`docs/architecture.md` §11): a phase's settings overlay sits above every layer of `getEffectiveSetting`; unreadable scenario state halts the challenge (never a silent restart); the runner re-reads live state before each action and persists progress after each one, so a resumed rule never repeats a landed spend.
- **Security invariants** (details/limits in `docs/architecture.md` §10): keep `contextIsolation` on, `nodeIntegration` off, and the sandboxed-preload / `window.api`-only exposure — regressing any is a severe-vuln class; keep the `isTrustedSender` frame check on every invoke; never log a raw headers/token object (redaction is key-allowlisted, not exhaustive — it only guards the key names it lists).

## File Management

- **Documentation Policy**: Do not create markdown files, README files, or other documentation unless explicitly requested by the user.
- **Prefer Editing**: Always edit existing files rather than creating new ones when possible.

## Testing Standards

- **Test Organization**: All test files must be placed in the `tests/` directory following proper Jest conventions and structure.
- **Mock Configuration**: Never use `mock: false` in any Jest or testing commands - use proper mocking strategies instead.
- **Mocking ES modules**: `src/` is `import`/`export`, compiled for Jest by swc with its standard interop. Two consequences:
    - A real module's exports are non-configurable getters, so `jest.spyOn` / property assignment on it throws ("Cannot redefine property"). To spy on a real module (or a Node builtin such as `node:fs`), give it a partial mock first: `jest.mock(p, () => ({ __esModule: true, ...jest.requireActual(p) }))`. For a builtin that packages default-import (fs), also pass `default: <the real module>`.
    - `import * as x` of a factory mock _without_ `__esModule` gets a copy of the factory object, so a test that later replaces a property on the mock (`mod.fn = jest.fn()`, `jest.spyOn(mod, …)`) or compares identity is not seen by the code under test. Put `__esModule: true` in any factory whose properties a test replaces. Changing a `jest.fn()` in place (`.mockReturnValue`, `.mockImplementation`) works either way.
- **100% coverage gate**: CI fails on anything below 100% — Jest via `coverageThreshold` (all four metrics over `src/ts/**` **and** `scripts/**`, `pnpm test:coverage`; `tests/helpers/swc-transformer.cts` wraps @swc/jest so swc's generated `export` getters don't count as statements), Android via `./gradlew jacocoTestCoverageVerification` (zero missed on every JaCoCo counter). New code ships with tests; `istanbul ignore` is only for branches genuinely unreachable under Jest, with a comment saying why. Scripts gate their CLI entry with `runIfMain(require.main, module, main)` (`scripts/lib/run-if-main.ts`), never an inline `require.main === module` — that branch can't run under Jest.

## UI/UX Standards

- **Styling Framework**: GUI application uses Tailwind CSS + DaisyUI for all styling components
- **Custom CSS Policy**: No custom CSS is allowed except for the predefined Latvian color theme (already defined in the project)
- **Component Consistency**: Follow DaisyUI component patterns and conventions for consistent user experience

## Renderer / UI

> Scope: `## UI/UX Standards` above governs styling policy (Tailwind/DaisyUI/theme); this section governs component & data-flow conventions. Deep reference: `docs/architecture.md` §8–9.

- **Backend access**: all backend calls go through `window.api.*` via `src/ts/react/api/` only — `useIpcQuery.ts` / `useAsyncIpcAction.ts` for queries and actions, `ipc.ts` for one-shot calls, event subscriptions and best-effort logging (`logRendererError`) — **no per-platform branching in components**. Oxlint rejects `window.api` / `globalThis.api` access anywhere else under `src/ts/react/`.
- **Structure**: no router (mount entry points `mountApp`/`mountLogin`); no toast lib — inline DaisyUI `alert` + `ui/ErrorBoundary`. User-facing error text follows _what happened → why → what next_, translated, never raw status codes at the user.
- **Primitives & theme**: reuse `src/ts/react/components/ui/` primitives; new modals **must** use `ui/Modal.tsx` (owns the a11y focus-trap bar). Theme = DaisyUI `data-theme`, no `dark:` variant. High-frequency ticks via `@preact/signals` (`useTimers`) to avoid re-rendering the challenge list.
- **i18n mandatory**: user-facing strings via `useTranslation().t()`, added to **both** `src/ts/core/translations/english.ts` and `latvian.ts`. Internal/log strings stay English.

## Code Quality

- **DRY Principle**: Prioritize code reuse over duplication. Extract common functionality into shared utilities, hooks, or components
- **Shared Logic**: Create reusable functions and modules that can be utilized across both Electron and CLI implementations

## Configuration Management

- **Settings Architecture**: Settings facade lives at `src/ts/core/settings.ts`. Schema (keys + defaults + validation) is the facade `src/ts/core/settings/schema.ts` over the group modules and `validators.ts` in `src/ts/core/settings/schema/` (private to it — import the facade); the persistence wrapper is `src/ts/core/settings/storage.ts`, over the transport the platform builds (`platform().storage`: fs on Electron/CLI/web in `platforms/node/`, `@capacitor/preferences` in `platforms/webview/`, the native bridge in `platforms/headless/`). The facade's internals (load/save/import in `settings/persistence.ts` + its `settings/persistence/` siblings + `settings/legacyImport.ts`, overrides, title rules, profiles, title pins, reset) live in sibling modules under `src/ts/core/settings/` and are private to it — Oxlint rejects importing them from outside that directory. Always go through the facade. `loadSettings` validates what it reads (`dropInvalidValues` in `settings/persistence.ts`): a top-level value of the wrong type, a `challengeSettings` container of the wrong kind, or a schema value its zod validation rejects is dropped for the default and logged once — so a setting read returns what its type says. Don't re-guard setting values downstream; widen the load-time check instead.
- **Settings files**: the stored shape (`config.json`, the import and its marker, recovery states) is described in `docs/architecture.md` §7 — read it before touching `settings/persistence.ts` or `legacyImport.ts`.
- **Environment Variables**: Do not use environment variables (.env files) for application configuration - use the established settings logic instead
- **Configuration Consistency**: Ensure settings are accessible and consistent between GUI and CLI interfaces

## Key Commands

> Use **pnpm 12+**, pinned by `packageManager`. Bootstrap with `corepack enable`. The `npm` CLI is not supported.

Before changing build scripts, packaging, or development commands, read [Development command reference](CONTRIBUTING.md#development-command-reference).

- **Dev**: `pnpm dev`.
- **CLI**: `pnpm cli:start`, `pnpm cli:vote`, `pnpm cli:status`, `pnpm cli:login`, `pnpm cli:help`.
- **TypeScript scripts**: use `node --import tsx scripts/….ts` for scripts that run `src/` or `scripts/` code. This preserves CommonJS globals. The electron-builder `afterPack` hook and Oxlint `jsPlugins` rules are `.mts`. Node strips their types natively. They must not use CommonJS globals.
- **Build**: `pnpm build:mac`, `pnpm build:win`, `pnpm build:linux`, `pnpm build:android`, `pnpm build:cli:all`. Each has a `:lite` twin without the vision model or runtime. Build CLI targets on their native architecture. Do not strip CLI binaries or use UPX. Read the reference for prerequisites.
- **Settings**: `pnpm settings:get`, `pnpm settings:set <key> <value>`, `pnpm settings:schema`, `pnpm settings:reset`.
- **Tests**: `pnpm test`, `pnpm test:watch`, `pnpm test:coverage`. Place React `.test.tsx` files under `tests/react/`. Other tests use `.test.ts`.
- **Checks**: `pnpm lint`, `pnpm lint:fix`, `pnpm format`, `pnpm typecheck`, `pnpm knip`, `pnpm size`, `pnpm size:cli`. After intentional renderer bundle growth, run `pnpm size:update` and commit `.size-baseline.json`.
- **README versions**: run `pnpm verify:readme`. Use `pnpm update:readme` to synchronize versions with `package.json`. Release CI rejects drift.
- **Lexicon**: after editing `scripts/lexicon-concepts.json`, rerun `pnpm fetch:embeddings`. Then use `pnpm build:lexicon` and `pnpm verify:lexicon`.
- **Web shell**: `pnpm web`, with optional `--port=<n>`. Every `/api/` request needs the per-run token from the printed URL fragment.
- **Notices**: after any dependency change, run `pnpm build:notices`. CI checks the generated notices.
- **Android dependencies**: after any graph change, including Capacitor bumps, run `scripts/android-verification-metadata.sh` and commit its output. Read the reference for prerequisites.

## Dependencies & Type Checking

Before changing dependencies, types, lint, or test conventions, read [Dependency and type reference](CONTRIBUTING.md#dependency-and-type-reference).

- **Intentional pins**: Prettier follows `4.0.0-alpha` under `next`. Electron-builder follows `v26`. Do not downgrade these to `latest` or merge such bot PRs. Electron-updater stays on `latest`. Other dependencies stay on exact latest stable. When bumping dependencies, check `npm view electron-builder dist-tags` manually.
- **Overrides and ignores**: `pnpm-workspace.yaml` contains exact CVE override pins and advisory ignores. After lockfile changes, run a full `pnpm audit`. Recheck glob when Jest moves beyond glob 13. Remove an override or ignore once upstream leaves the vulnerable range. Read the reference for the advisory scope and global-agent proxy behavior.
- **Build scripts**: keep `allowBuilds:` in `pnpm-workspace.yaml` minimal. Each approved native postinstall script can execute arbitrary code.
- **Compiler**: TypeScript 7 is a checker only (`tsc --noEmit`). esbuild bundles, swc compiles for Jest, and `tsx` runs scripts. App, scripts, and tests stay strictly checked.
- **Types**: type `require()` values where produced. Preserve test mock and global setup order. Use typed mocks, never bare `jest.Mock`. Use `invalid<T>(…)` for wrong-typed inputs and partial fixtures, never `as unknown as T`. In `.tsx`, use `<T,>` for an unconstrained generic arrow. Import shared GuruShots and settings shapes instead of redeclaring them. Give state, refs, contexts, and callbacks type arguments instead of casts.
- **Boundaries**: declare precise parameter types. Do not widen them to `unknown` for loose callers. API responses use typed optional or nullable shapes. `makePostRequest<T>` produces them, so endpoint wrappers must not cast. IPC handlers declare renderer argument types and validate at runtime. `invokeHandler` is the single argument-dispatch boundary. `IpcHandler` uses `never[]`.
- **Unknown values**: use `unknown` for validators, unvalidated persisted JSON or user documents, caught errors, and logger payloads. Narrow values before use with existing predicates. Read caught messages through `errorMessage`. Never use or leak `any`. Do not use `@ts-ignore`, `@ts-expect-error`, or `@ts-nocheck`.
- **Lint**: Oxlint covers `src/`, `scripts/`, and `tests/`. Use `node:` imports. Unused arguments and catch bindings may use `_` prefixes. Lint enforces hooks, accessibility, facades, renderer access, layers, frame sends, promises, and unsafe-value checks. Runtime packages belong in their runtime layer. Type-only imports and `typeof import()` are exempt. Every `<label>` must name or wrap its control. Frame-send exemptions are pinned in `tests/ci-validation.test.ts`.
- **Promises and formatting**: `void` does not handle a rejected promise. Add `.catch` or try/catch when rejection matters. Bare `void` is only for inconsequential calls. Prettier owns formatting. Dependabot updates Oxlint and `oxlint-tsgolint` together.
- **Repository analysis**: use Ripwire for structural analysis. Use `tsc` for compiler-exact type diagnostics.
- **Hooks**: Lefthook fixes and restages whole files, including partial staging. After an `--ignore-scripts` install, run `pnpm exec lefthook install`.
- **CI checks**: run `pnpm audit --prod --audit-level=high` for shipped dependencies. See the reference for full audit, CodeQL, size, knip, type-check jobs, and runner constraints.

## Git Operations

- **Push Restrictions**: Never push changes to remote repositories under any circumstances. All git operations must remain local only.
- **Commit Policy**: Adding commits and performing git read operations (status, log, diff, etc.) are permitted and encouraged for development workflow.
- **File Reset Prohibition**: Never use `git checkout` to reset or revert files under any circumstances. This includes avoiding commands like `git checkout -- <file>` or `git checkout HEAD <file>`.
- **Branch Operations**: Local branch operations are allowed, but all changes must remain in the local repository.
- **Safe Git Commands**: Stick to read-only git commands (status, log, diff, show) and local commit operations only.

## Development Commands

- **Linting & types**: Run `pnpm lint` and `pnpm typecheck` after code changes. `tsc` runs as a checker only (strict over `src/ts`), and Oxlint lints `src/`, `scripts/` and `tests/`; see **Dependencies & Type Checking**.
- **Testing**: Use proper Jest test commands as defined in package.json
- **Testing Completion**: All tests must pass regardless of code changes (even if they are not related to the code being changed)
- **Logger**: Use `import * as logger from './logger'` (`src/ts/core/logger.ts`). Prefer category-scoped logging: `logger.withCategory('voting').info(msg, data)`. Never use `console.log` — fallback to `console.*` only in bootstrap code where the logger module is genuinely unavailable. The logger reads `platform()` when it loads, so a shell's `platform.ts` must install before it: never add a static import of the logger (or anything that reaches it) to a shell platform module's load chain.
